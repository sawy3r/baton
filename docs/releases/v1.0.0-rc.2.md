# Baton v1.0.0-rc.2 — the portable delivery kit

RC2 turns Baton’s small trust protocol into a usable, platform-neutral kit for
Claude Code, Codex, and autonomous engines.

```text
approved Plan
  -> Implementer design
  -> Captain
  -> Implementer build and proof
  -> fresh Verifier
  -> exact Merge
```

Baton defines that protocol, the durable records, and deterministic local
actions. Sworn is the reference engine that can orchestrate them autonomously.
Baton itself does not run models, manage inference, hold provider credentials,
or choose a model.

## What ships

### Five principles and five responsibilities

The trust kernel remains:

1. **Bounded authority**
2. **Durable truth**
3. **Real evidence**
4. **Independent verification**
5. **Safe composition**

RC2 makes the operating responsibilities explicit: Planner, Implementer,
Captain, Verifier, and Merge. These are authority boundaries, not a requirement
for five providers or processes.

Normal work has four durable handoffs:

```text
plan.md -> design.md -> proof.md -> status.json
```

`status.json` is the sole authored JSON Schema and covers both work and release
assembly. A `baton.board/v1` document is a derived read-only projection, not a
second status schema or action surface.

### Five concise operations

The portable package contains:

- `baton-plan`
- `baton-implement`
- `baton-design-review`
- `baton-verify`
- `baton-merge`

Claude Code and Codex Skills contain byte-identical canonical operation
regions. A project install wins over a user install, so a repository can pin
its own Baton package.

### Independent tracks and whole-product verification

Separate tracks may be active together while work inside each track remains
serial. Track Merge freezes and composes only passed owner heads. When every
track is present, Merge prepares an assembly proof naming each exact component;
a fresh read-only Verifier checks the complete product before release Merge
compares and updates the expected target.

Work PASS is therefore not a release claim, and “merged” does not silently mean
“deployed.”

### Transactional installation

The Claude Code and Codex launchers support:

- user and Git-project scopes;
- non-mutating dry-run;
- explicit non-interactive confirmation;
- package manifests and no-op repeat installation;
- transaction journals, interruption recovery, rollback, and uninstall; and
- collision, ownership, symlink, and modified-file refusal.

The Claude user installer can migrate only the exact audited Baton v0.16
installation: 79 support files, eight commands, and the exact trailing
instruction block. It preserves unrelated commands and instruction bytes and
stops before mutation on any fingerprint mismatch. It installs no permanent
global `CLAUDE.md` or `AGENTS.md` block.

### One thin board

The package includes:

- an owner-aware JSON oracle;
- a safe terminal renderer; and
- a loopback GET/HEAD-only WebUI.

All three show the same captured release, track, work, assembly, diagnostic,
and next-operation facts. They cannot advance the lifecycle.

### One common driver seam

`baton.driver/v1` is a small process contract between an engine and a runner.
The same driver can serve every Baton responsibility. The engine supplies an
explicit model string or deliberate `null` on each invocation.

Drivers do not choose default models, retry, fall back, rotate providers,
manage credentials, or reinterpret a runner response as a Captain decision,
Verifier verdict, or Merge fact.

```text

```

The Node profile covers records, operations, adapters, isolated installation,

The manual real-Git dogfood completed 17 meaningful checkpoints across three
tracks, including a Captain REVISE, Verifier FAIL/repair/PASS, an operational
`NO_VERDICT` with unchanged durable state, dependency refusal, exact track
composition, fresh read-only assembly verification, and target
compare-and-set. That is portable evidence, not a claim about an engine’s
scheduler or provider isolation.

## Autonomous-engine status

All 12 autonomous cases are still `NOT RUN`.

They cover boundaries a portable library or manual dogfood cannot prove,
including authenticated approval, concurrent writer exclusion, credential
isolation, fresh context, read-only dispatch, timeout, cancellation, crash
recovery, and final effects. Sworn must run them through its actual binary,
scheduler, persistence, driver, workspace, and Git boundaries before any result
can change to PASS.

RC2 therefore makes no autonomous Sworn conformance claim. Final `v1.0.0` waits
for that evidence.

## What changed from RC1

RC1 explored a smaller four-record submission/verdict model. RC2 replaces that
current surface with the repository-native lifecycle proven during B1–B4:

- one work/assembly status schema instead of four delivery-record schemas;
- exact Plan, design, proof, and status handoffs;
- an explicit Captain boundary before implementation;
- track ownership, serial work, composition, and fresh assembly verification;
- deterministic record/Git actions and one read-only board;
- generated Claude Code and Codex Skills;
- transactional local installers; and
- a common role-independent driver contract.

The [RC1 release note](v1.0.0-rc.1.md) remains unchanged as historical
evidence.

## Upgrade and history

Baton 0.x remains immutable at
[`v0.16.0`](https://github.com/sawy3r/baton/tree/v0.16.0). The exact Claude
installer migration is recoverable, but RC2 does not read or reinterpret old
delivery records. Modified legacy installations require an explicit manual
decision; the installer fails closed rather than guessing.
