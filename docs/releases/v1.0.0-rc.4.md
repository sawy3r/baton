# Baton v1.0.0-rc.4 — the lightweight loop

RC4 keeps the part of Baton that makes autonomous delivery trustworthy and
removes the procedure that made ordinary iteration expensive.

```text
approved plan and slices
  -> Implementer design TL;DR
  -> Captain decision
  -> implementation candidate
  -> fresh Verifier decision
  -> merge the exact candidate that passed
```

Baton is the protocol. Sworn is the engine. Scheduling, retries, recovery,
worktrees, model drivers, credentials, telemetry, and hosted operation belong
to Sworn or another compatible engine.

## What changed

### One plan, stable slices

A release now advances through forward-only plan revisions at one path. Slice
identities remain stable through design revisions and implementation repairs.
Changing one slice retains the others unless their contract or actual consumed
product input changed.

Ordered slices remain serial inside one track. Independent tracks can progress
together. The plan parser validates one combined delivery graph across track
gates, same-track serial order, explicit dependencies, and consumed inputs.
The action surface and Git-derived reader also reject out-of-order same-track
work.

### Compact receipts instead of document churn

The normal durable surface is one approved plan plus small machine-written
receipts. Git, candidate commits, checks, and code carry the implementation
evidence.

RC4 no longer requires a hand-authored `status.json`, `design.md`, `proof.md`,
transition program, or packaged fake driver. Longer design or evidence
documents remain optional when a particular change genuinely needs them.

The strict `receipt-v1` envelope binds:

- the applicable plan and stable slice contract;
- the design or implementation attempt;
- Captain and fresh Verifier decisions;
- the exact candidate, product tree, inputs, and check-result digest; and
- the expected target and exact merge result.

Runner failures, timeouts, duplicate dispatch, stale board output, and
interrupted effects produce no Baton verdict. The engine retries or reconciles
them without inventing approval, `PROCEED`, `PASS`, or `MERGED`.

### Git-derived relay board

The JSON oracle, safe terminal renderer, and loopback browser board now derive
the most advanced trustworthy state from the plan, receipts, exact refs, and
Git objects. The oracle publishes one ephemeral typed graph over the approved
plan; it is never persisted or used as action authority. The browser renders
that graph as a relay: Plan starts the route, slices carry work through track
lanes and declared handoffs, Assembly is the final exchange, and Merge is the
finish. The browser does not reconstruct readiness or dependency closure.

The installer includes the complete receipt/state/action dependency closure
and all three read-only board views.

## Compatibility

RC4 intentionally does not import or dual-write RC2/RC3 status records. Their
tagged code and Git history remain immutable archaeology. Installers can still
transactionally migrate only the exact audited Baton v0.16 user installation;
modified legacy installations fail closed.

All autonomous-engine cases remain `NOT RUN`. Portable success does not claim
that an engine proved scheduling, process or credential isolation, fresh
context, retries, cancellation, recovery, drivers, telemetry, or final effects.
Sworn must demonstrate those through its real binary.

## Install

The recommended route is agent-led installation. Ask Claude Code or Codex to
clone the exact `v1.0.0-rc.4` tag, read `INSTALL.md`, show the matching
user-scope dry-run, and wait for approval before applying it. The shell
installers remain available as the secondary route.

Publication, tagging, public release assets, and website updates remain
separate protected steps after review and merge.
