# Baton v1.0.0-rc.9 — agent-led installation

RC9 removes the client-maintenance layer from Baton installation. The agent
already running in a tool now discovers that tool's current skills directory,
shows the exact change, waits for approval, installs one neutral payload, and
proves native discovery.

This is an installation and packaging boundary change. The Baton protocol,
operations, receipt contract, schemas, delivery lifecycle, board, and engine
integrations are unchanged.

## One standalone payload

The generated [`skills/`](../../skills/) payload contains exactly five
standalone directories:

```text
baton-plan
baton-implement
baton-design-review
baton-verify
baton-merge
```

Each `SKILL.md` contains the exact canonical operation source. `baton-plan`
also bundles `templates/plan.md` at the relative path named by the operation.
No installed skill depends on a separate support package or client-specific
bridge.

`skills/.baton-payload.json` binds every payload file to:

- release `v1.0.0-rc.9`;
- its source path and SHA-256;
- its generated SHA-256; and
- the complete payload digest.

The RC9 payload digest is:

```text
sha256:792a1a558c8b228801f4c7fcb55b89a1272d00651baa2e24e240b46ba0a5519c
```

## Agent-led safety

Baton no longer ships client wrappers, selectors, path tables, host adapters,
or a general installer. The installing agent resolves the destination from
the current tool's documentation or environment and presents it for approval.

Approval is bound to the exact release commit, payload digest, canonical
destination, complete relative-path change set, and observed destination
state. The agent rechecks every field immediately before effects and shows a
new preview if anything changed.

An incomplete exact payload is neither adopted as installed nor removed
automatically; it requires a new preview and user direction. Removal is
eligible only for the complete byte-identical expected path set with no
missing, extra, symlink, or special entries. The final recheck protects the
approved state, not against a concurrent writer afterward. After interruption,
the agent inspects the destination and shows a new preview.

## Compatibility boundary

RC9 never overwrites RC2–RC8 state. An older installation must be identified
and removed with that exact immutable release's own safe uninstall before RC9
is eligible. Unknown, modified, or ambiguous ownership stops.

For updates between neutral payload releases, the agent removes the exact
complete old payload after approval, then separately previews and installs the
new exact payload. There is no in-place byte adoption.

Git retains every retired installer and historical fixture. They are
archaeology and release-specific removal tools, not live RC9 product code.

## Publication evidence

Release checks must cover deterministic generation, exact canonical regions,
bundled resources, immutable provenance, approval binding, final pre-effect
recheck, partial-state refusal, exact removal, and interruption re-preview.
Before publication, clean-context native discovery must also be checked across
several materially different Agent Skills clients as release evidence, not as
a maintained support allow-list.
