# Baton v1.0.0-rc.1 — the trust kernel

This is the first release candidate for the rebuilt Baton protocol. It replaces
the Baton 0.x procedural system with a smaller behavioral contract for
autonomous software delivery whose completion claims can be trusted.

## What changed

### Five load-bearing principles

Baton Core is now five principles:

1. **Bounded Authority** — autonomy stays inside an authenticated, approved
   delivery contract.
2. **Durable Truth** — validated records and repository facts outrank session
   prose or mutable projections.
3. **Real Evidence** — proof identifies one exact candidate and exercises the
   boundary claimed by each acceptance criterion.
4. **Independent Verification** — no builder certifies its own candidate; a
   fresh verifier binds its verdict to an immutable submission.
5. **Safe Composition** — only the exact verified candidate may be integrated,
   under an expected target revision that fails closed when the target moves.

The normal path needs two model-role invocations: builder and fresh verifier.
The engine owns deterministic mechanics, containment, persistence, recovery,
repository measurement, and authorized effects.

### Six strict contracts

Four portable delivery records carry the work:

- `delivery-plan-v1`;
- `submission-v1`;
- `delivery-verdict-v1`; and
- `delivery-board-v1`.

`assurance-policy-v1` binds Standard checks and optional Assured packs.
`control-receipt-v1` records authority approval, verifier dispatch, and
integration effects without creating extra delivery stages.

Verdicts route through four typed outcomes: `PASS`, `FAIL`, `SPEC_BLOCK`, and
`INCONCLUSIVE`. A board is a read-only projection of durable records, engine
events, effect receipts, and repository facts; editing it cannot change state.

### Assurance selected by risk

Every work unit starts with the Standard profile: exact records, relevant
deterministic checks, acceptance-linked evidence, fresh verification, and safe
integration. Assured delivery adds only the versioned packs selected by approved
policy or a deterministic risk trigger. Security, privacy, money, data change,
public contracts, production, regulation, design decisions, and critical
journeys no longer impose universal ceremony on unrelated work.

### Behavioral conformance

Conformance is a corpus, not a prompt or brand claim. This candidate ships:

- 7 strict I-JSON cases;
- 2 RFC 8785 canonicalization vectors;
- 46 schema fixtures;
- 99 executable cross-record cases; and
- 18 real-boundary engine scenarios covering Git, persistence, subprocess,
  sandbox, authority, recovery, and integration behavior.

The portable checker passes the first four groups. The 18 engine cases remain
`NOT RUN` until exercised through a real engine binary and its actual
boundaries. This is why this release is `rc.1`, not final `v1.0.0`.

## Clean break from Baton 0.x

Baton 1.x does not read, migrate, or silently reinterpret Baton 0.x records.
The 0.x protocol remains immutable at
[`v0.16.0`](https://github.com/sawy3r/baton/tree/v0.16.0) for archaeology and
existing consumers.

The following 0.x implementation procedures are deliberately absent from the
new core:

- canonical prompts, slash commands, and coding-tool installers;
- mandatory Planner, Captain, Implementer, and Integrator manuals;
- mutable slice-status machinery and prescribed Git/worktree choreography;
- universal RTM, journey, design, maintainability, and LLM-review cascades; and
- model/provider policy.

Projects and engines may still use those techniques when their risk warrants
them. They are no longer prerequisites for every conforming delivery.

## Validation for this release

```text
PASS 7 strict JSON cases, 2 canonicalization vectors, 46 schema fixtures,
     and 99 executable cross-record cases
NOT RUN 18 real-boundary engine cases (requires a conforming engine adapter)
```

All repository JSON parses, `baton/CORE.md` is 584 words, and the complete
normative surface is 4,946 words—within the release budget of 1,000 and 6,000
words respectively.

## Path to final v1.0.0

Final `v1.0.0` requires a real engine to pass every published engine case through
its built binary, Git implementation, persistent store, subprocess containment,
authority resolver, recovery path, and integration boundary. Sworn is the
reference implementation, not a privileged interpretation of Baton.
